# Резюме с сайта вакансий как источник данных сессии

Статус: утверждённое направление для реализации.
Дата фиксации: 13 сентября 2026 года.
Назначение: этот документ можно передать новому чату GPT как исходный контекст и сразу переходить к планированию и реализации.

## 1. Коротко: что нужно сделать

Убрать из приложения создание, редактирование и долговременное хранение профилей и резюме кандидата. При создании каждой сессии приложение должно получать актуальное резюме с того сайта вакансий, на котором запускается сессия:

- HH.ru — из резюме HH.ru;
- HireHi — из резюме HireHi;
- Zarplata.ru — из резюме Zarplata.ru;
- каждый будущий сайт — через собственный механизм его адаптера.

Пользователь указывает прямую ссылку на резюме либо выбирает резюме в уже авторизованном аккаунте сайта. Адаптер конкретной площадки открывает страницу, извлекает доступные поля и возвращает общий нормализованный снимок. Снимок фиксируется только на время сессии, чтобы поиск, оценка, письмо и восстановление после сбоя использовали одну версию данных.

Источник истины — сайт вакансий. Изменять резюме внутри приложения нельзя: пользователь изменяет его на исходном сайте и запускает новый импорт.

## 2. Подтверждённые продуктовые решения

Эти решения уже согласованы и не требуют повторного обсуждения перед началом реализации:

1. Внутренний редактор профиля и резюме является лишним функционалом и должен быть удалён.
2. Импорт PDF, DOCX и TXT как основной пользовательский путь должен быть удалён вместе с хранением исходных файлов в `data/resumes`.
3. Каждая сессия использует резюме с того же сайта, где выполняется поиск/работа с вакансиями.
4. Пользовательский интерфейс импорта может быть одинаковым, но извлечение всегда site-specific.
5. Нельзя делать один универсальный HTML- или PDF-парсер для всех сайтов.
6. Каждый адаптер обязан иметь собственный валидатор URL, навигацию, локаторы и extractor резюме.
7. После извлечения все адаптеры возвращают общий строго типизированный снимок.
8. Разные сайты имеют разные секции и полноту данных; общая схема не должна уничтожать уникальную информацию сайта.
9. Модель оценки вакансии и планировщик поиска не получают прямые персональные данные.
10. Финальное сопроводительное письмо может содержать ФИО и контакты. По умолчанию реальные значения подставляются локально после генерации текста.
11. Для восстановления активной сессии допустим временный снимок. Долговременный пользовательский профиль после завершения сессии не нужен.
12. Сырой HTML, PDF, изображения страниц, cookies и browser storage не сохраняются.

## 3. Что было проверено на реальных сайтах

### 3.1. HH.ru

На HH.ru существует режим видимости «Доступно только по прямой ссылке». Проверка выполнена в отдельном браузере без авторизации:

- ссылка вида `https://hh.ru/resume/<resume-id>` открылась без аккаунта;
- HH.ru перенаправил запрос на региональный поддомен вида `https://<region>.hh.ru/resume/<resume-id>`;
- страница показывала гостевой интерфейс с кнопкой входа;
- само резюме, включая профессиональные поля и контакты, было доступно.

Следовательно, для такого режима ссылка является достаточным способом чтения резюме без HH-сессии. Реальный идентификатор и реальные персональные данные пользователя в документацию не включать.

Структура HH.ru включает, среди прочего:

- ФИО, пол/возраст, местоположение и контакты;
- желаемую должность, специализации и форматы занятости;
- переезд и командировки;
- опыт работы и описания достижений;
- навыки и уровни владения;
- образование и языки;
- гражданство и разрешение на работу;
- настройки анонимности и видимости.

Публичная ссылка может перенаправляться на другой региональный поддомен. Реализация не должна быть привязана только к `krasnoyarsk.hh.ru`, но должна строго отличать настоящий поддомен `hh.ru` от похожего домена злоумышленника.

### 3.2. HireHi

Проверенный пользовательский путь:

```text
Профиль → Резюме → Действия → Предпросмотр → Скопировать ссылку
```

HireHi предоставляет публичную HTML-страницу вида `https://hirehi.ru/resume/<opaque-id>`, а также ссылки на PDF и ATS PDF. Для импорта предпочтителен HTML, потому что он уже содержит структурированные секции и не требует PDF-парсинга.

В HireHi встречаются поля, которых может не быть или которые иначе представлены на HH.ru:

- отдельный грейд;
- проекты, награды и достижения;
- курсы;
- RU/EN-версии резюме;
- основной статус резюме;
- локация, релокация, формат и тип занятости;
- ATS-версия;
- публичные контакты и ссылки.

### 3.3. Zarplata.ru

Путь, URL и структура публичного/профильного резюме ещё должны быть исследованы отдельно перед реализацией extractor-а. Нельзя копировать локаторы HH.ru или предполагать одинаковые секции.

Исследование должно определить:

- существует ли доступ по прямой ссылке без авторизации;
- допустимые домены и редиректы;
- список резюме в аккаунте;
- структуру полной и анонимной страницы;
- наличие скачивания и скрытых секций;
- локализацию дат, зарплат и форматов работы.

## 4. Целевой пользовательский путь

### MVP: прямая ссылка

1. Пользователь создаёт сессию и выбирает сайт.
2. Форма показывает поле «Ссылка на резюме на <сайт>».
3. Пользователь вставляет прямую ссылку.
4. Приложение проверяет домен и формат URL до открытия страницы.
5. Соответствующий адаптер открывает резюме в BrowserExecutor.
6. Адаптер извлекает нормализованный снимок.
7. UI показывает read-only предпросмотр:
   - название/целевая роль;
   - время обновления, если доступно;
   - найденные разделы;
   - отсутствующие или скрытые обязательные поля;
   - предупреждение о публичности ссылки;
   - какие данные получит модель.
8. Пользователь подтверждает резюме и запускает сессию.
9. Сессия фиксирует эту версию снимка и не меняет её посреди работы.

### Следующий этап: выбор из аккаунта

Если пользователь уже вошёл на сайт в браузерном профиле приложения, адаптер может показать список его резюме и позволить выбрать одно без копирования ссылки.

Это улучшение использует тот же extractor и ту же нормализованную схему. Оно не должно создавать второй параллельный механизм обработки резюме.

### Несколько резюме

Безопасный MVP — одно явно выбранное резюме на одну сессию. Схема может позволять несколько снимков в будущем, но их нельзя автоматически объединять: разные резюме могут быть предназначены для разных профессий и содержать противоречащие настройки.

## 5. Контракт адаптера

Site-specific навигация и извлечение остаются в `backend/adapters`. Общая бизнес-логика, хранение и модельные представления находятся вне адаптеров.

Рекомендуется отдельная optional capability, а не разрастание обязательного `JobSiteAdapter` для сайтов без резюме:

```python
class ResumeRef(BaseModel):
    source_site: str
    external_id: str
    url: str
    title: str | None = None
    language: str | None = None


class ResumeImportCapability(Protocol):
    def validate_resume_url(self, url: str) -> ResumeRef:
        """Проверить и нормализовать пользовательскую ссылку без навигации."""

    async def list_resume_refs(self, page) -> list[ResumeRef]:
        """Опционально: получить резюме из авторизованного аккаунта."""

    async def open_resume(self, page, ref: ResumeRef) -> None:
        """Открыть только разрешённую страницу и проверить конечный URL."""

    async def extract_resume(self, page, ref: ResumeRef) -> SiteResumeSnapshot:
        """Извлечь видимые данные без оценки и вызова модели."""
```

Manifest адаптера должен сообщать capability:

```python
supports_resume_import: bool
supports_public_resume_url: bool
supports_account_resume_list: bool
```

Рекомендуемое размещение:

```text
backend/adapters/hh/resume.py
backend/adapters/hh/resume_locators.py

backend/adapters/hirehi/resume.py
backend/adapters/hirehi/resume_locators.py

backend/adapters/zarplata/resume.py
backend/adapters/zarplata/resume_locators.py

backend/adapters/base/resume_protocol.py
```

Адаптер делает только следующее:

- валидирует site-specific URL;
- управляет site-specific навигацией через разрешённый браузерный слой;
- ждёт готовности страницы;
- определяет закрытую, удалённую, анонимную или неполную страницу;
- извлекает видимые поля;
- сопоставляет их с общей схемой и сохраняет provenance.

Адаптер не должен:

- вызывать модель;
- оценивать пригодность кандидата;
- решать, какие данные отправить модели;
- хранить резюме или контакты;
- писать сопроводительное письмо;
- использовать скрытые API сайта;
- выполнять произвольный JavaScript со страницы.

## 6. Общая схема снимка

Текущий `ResumeData` слишком узок для объединения HH.ru, HireHi и будущих сайтов. Нужна расширенная схема, которая сохраняет значения, статус доступности и происхождение.

Иллюстративный контракт:

```python
class FieldAvailability(StrEnum):
    PRESENT = "present"
    NOT_PROVIDED = "not_provided"
    HIDDEN = "hidden"
    UNSUPPORTED = "unsupported"
    PARSE_ERROR = "parse_error"


class SourceField[T](BaseModel):
    value: T | None = None
    availability: FieldAvailability
    source_section: str | None = None


class SiteResumeSnapshot(BaseModel):
    schema_version: int
    extractor_version: str
    source_site: str
    source_resume_id: str
    source_url_hash: str
    source_updated_at: datetime | None
    imported_at: datetime
    content_hash: str

    identity: ResumeIdentity
    contacts: ResumeContacts
    target: ResumeTarget
    location: ResumeLocation
    experience: list[ResumeExperience]
    projects: list[ResumeProject]
    skills: list[ResumeSkill]
    education: list[ResumeEducation]
    languages: list[ResumeLanguage]
    courses: list[ResumeCourse]
    certifications: list[ResumeCertification]
    awards: list[ResumeAward]
    portfolio: list[ResumePortfolioItem]
    about: SourceField[str]
    additional_sections: list[AdditionalResumeSection]
    coverage: ResumeCoverage
```

Точный состав Pydantic-моделей определяется реализацией, но должны покрываться:

- идентичность: ФИО, явно указанный пол, возраст/дата рождения, фото-флаг;
- контакты: телефон, email, мессенджеры, профессиональные ссылки;
- целевая роль, специализации, грейд, зарплата;
- типы занятости и форматы работы;
- локация, релокация, командировки, гражданство/разрешение на работу;
- опыт, обязанности и достижения;
- отдельные проекты;
- навыки и уровни;
- образование, языки, курсы, сертификаты, тесты;
- награды, портфолио, публикации и дополнительные секции.

### Почему нужен статус доступности

`null` недостаточно. Например:

- телефон может отсутствовать у пользователя;
- телефон может быть скрыт анонимным режимом;
- сайт может вообще не поддерживать телефон в резюме;
- extractor мог не найти изменившийся локатор.

Эти состояния приводят к разным действиям и не должны смешиваться.

### Дополнительные секции

Общая схема не должна быть «наименьшим общим знаменателем». Уникальная структурированная секция сохраняется так:

```json
{
  "type": "award",
  "title": "...",
  "text": "...",
  "date": "...",
  "source_site": "hirehi"
}
```

В `additional_sections` запрещено сохранять сырой HTML, DOM-атрибуты, scripts или инструкции страницы.

## 7. Представления для разных потребителей

Полный снимок никогда не отправляется всем компонентам без фильтрации. Из него детерминированно строятся разные views.

```python
snapshot.for_search_planning()
snapshot.for_matching()
snapshot.for_cover_letter()
snapshot.for_application_form()
```

### Поиск и оценка вакансии

Модель получает только профессиональные данные:

- целевую роль и специализации;
- опыт, обязанности и достижения;
- навыки;
- образование, курсы и языки;
- профессиональное описание;
- условия работы, важные для поиска.

Не передаются:

- ФИО;
- телефон, email и мессенджеры;
- фотография;
- точная дата рождения;
- публичная ссылка на резюме;
- другие прямые идентификаторы, не влияющие на соответствие вакансии.

### Сопроводительное письмо

Бизнес-требование: итоговое письмо может включать ФИО и выбранные контакты.

Безопасное поведение по умолчанию:

1. Модель получает профессиональный view, выбранный пользователем грамматический пол и `signature_policy`.
2. Модель пишет тело письма с placeholders либо без подписи.
3. Локальный composer добавляет подпись и подставляет реальные значения.

Пример:

```text
С уважением,
{{full_name}}
Telegram: {{telegram}}
Email: {{email}}
```

Так итоговое письмо содержит данные пользователя, но сами значения не попадают к внешнему провайдеру модели.

Если особое условие работодателя действительно требует естественного использования конкретного контакта внутри текста, возможна отдельная явно согласованная политика передачи минимального поля. Это исключение, а не default.

### Анкета отклика

ФИО и контакты для полей формы подставляются локально. Модель может определить смысл вопроса или выбрать допустимый тип ответа, но фактическое значение прямого контакта не требуется передавать модели.

### Грамматический пол

Пол нельзя выводить из имени. Допустимые источники:

- поле, явно присутствующее в резюме сайта;
- короткий session-scoped вопрос пользователю.

Если значение было получено с сайта, UI должен показать его в предпросмотре. При неоднозначности требуется подтверждение пользователя.

## 8. Временное хранение и восстановление

Полностью volatile-обработка несовместима с гарантированным восстановлением после сбоя. Поэтому нужно различать долговременный профиль и временный снимок активной сессии.

Рекомендуется отдельная таблица или защищённое session-scoped хранилище, например `session_resume_snapshots`:

```text
session_id                 unique foreign key
source_site
source_resume_id
source_url_encrypted       nullable
source_url_hash
professional_snapshot     JSON
private_identity_encrypted JSON/null
content_hash
schema_version
extractor_version
source_updated_at
created_at
expires_at
```

Правила:

- URL прямой ссылки считается чувствительным bearer-идентификатором;
- полный URL не попадает в события, ошибки, measurement reports и логи;
- raw HTML/PDF/DOCX/TXT не сохраняются;
- профессиональная и персональная части физически или логически разделены;
- активная сессия всегда использует зафиксированный `content_hash`;
- изменение резюме на сайте не меняет уже запущенную сессию;
- снимок удаляется после формирования финального результата и терминального перехода;
- удаление должно быть идемпотентным;
- при строгом режиме «только память» UI обязан предупредить, что автоматическое восстановление невозможно.

Точный период grace/retention перед удалением не согласован. Безопасный default — удалить сразу после успешной финализации сессии и отчёта.

## 9. Безопасность URL и браузера

Публичная ссылка содержит персональные данные и может работать как bearer capability. Требования:

1. Сначала определить adapter по явно выбранному сайту, а не доверять hostname из URL.
2. Разрешать только HTTPS.
3. Запрещать username/password в URL.
4. Запрещать произвольные порты.
5. Очищать fragment и необязательные tracking-параметры.
6. До и после каждого редиректа проверять hostname, scheme и допустимый path.
7. Защищаться от доменов вида `hh.ru.evil.example` и `evilhh.ru`.
8. Ограничить число редиректов, размер страницы и время ожидания.
9. Не использовать универсальный backend URL fetcher: открытие проходит через adapter и `backend/browser`.
10. Не передавать URL модели.
11. Не выполнять команды, инструкции или scripts, найденные в тексте резюме.
12. Весь текст резюме считать недоверенными данными и прогонять через существующую prompt-injection boundary.

Примеры базовых паттернов:

```text
HH.ru:    https://hh.ru/resume/<id>
          https://<approved-region>.hh.ru/resume/<id>

HireHi:  https://hirehi.ru/resume/<opaque-id>
```

Не принимать как исходную ссылку PDF/ATS endpoints, если доступна базовая HTML-страница.

## 10. Владение резюме и согласие

Публичность ссылки не доказывает, что пользователь владеет резюме. Иначе приложение можно использовать для обработки чужих персональных данных.

Предпочтительное подтверждение:

- в авторизованном режиме адаптер проверяет, что resume ID присутствует в списке резюме текущего пользователя;
- при импорте только по публичной ссылке пользователь явно подтверждает: «Это моё резюме, и я разрешаю использовать его данные для этой сессии».

Перед запуском нужно показать:

- какие секции извлечены;
- какие контакты обнаружены;
- какие данные будут переданы модели;
- что сама публичная ссылка доступна любому, кто её получил;
- когда локальный временный снимок будет удалён.

Нельзя писать «резюме никуда не загружается». Корректная формулировка:

> Не нужно загружать файл. Приложение считывает выбранное вами резюме с сайта вакансий, временно фиксирует данные для сессии и передаёт модели только необходимую часть.

### Текущее состояние

Сейчас проект содержит:

- `CandidateProfile` и `Resume` в `backend/persistence/models.py`;
- обязательный `JobSession.profile_id`;
- `ProfileMemory` и `SessionQuestion`, привязанные к profile ID;
- CRUD `/profiles` и `/profiles/{id}/resumes` в `backend/api/router.py`;
- файловый импорт через `backend/services/resume.py`;
- хранение исходников в `data/resumes`;
- большую страницу `ProfilePage` в `frontend/src/App.tsx`;
- `selected_for_matching` как долговременную настройку резюме;
- evaluator, search planner, writer и application answers, принимающие `profile` и `resumes`.

Поэтому изменение является не локальной заменой формы, а миграцией центральной модели кандидата.

### Целевые изменения backend

- добавить общий `SiteResumeSnapshot` и consumer views;
- добавить resume capability к registry/manifest адаптеров;
- реализовать отдельные HH, HireHi и Zarplata extractors;
- добавить сервис импорта и preview;
- привязать временный снимок к `JobSession`, а не к постоянному профилю;
- изменить evaluator/search planner/writer/application answers на session candidate context;
- разделить модельные payloads по назначению;
- заменить фактические контакты в writer payload на placeholders/signature policy;
- реализовать очистку snapshot после терминальной финализации;
- убрать file-import endpoints и локальные оригиналы;
- мигрировать или удалить связи с `CandidateProfile` и `Resume`.

### Целевые изменения frontend

- удалить создание/редактирование профиля;
- удалить создание, удаление, выбор и файловый импорт локальных резюме;
- удалить onboarding, требующий заранее созданного профиля;
- добавить site-specific поле ссылки в создание сессии;
- добавить кнопку проверки и read-only preview;
- показать coverage, скрытые поля и ошибки extractor-а;
- при недостающем критическом поле задать короткий session-scoped вопрос;
- добавить ссылку «Изменить резюме на исходном сайте»;
- не показывать полный raw URL после импорта.

### API-кандидаты

Названия можно скорректировать, но границы должны сохраниться:

```text
POST /resume-sources/preview
  { adapter_id, resume_url }
  -> sanitized preview + one-time preview token

POST /sessions
  { adapter_id, resume_preview_token, session settings }
  -> session with immutable resume snapshot
```

Preview token должен быть короткоживущим, одноразовым и не содержать raw URL на клиенте. Повторная серверная валидация перед созданием сессии обязательна.

## 12. Что делать с памятью ответов пользователя

`ProfileMemory` хранит пользовательскую информацию между сессиями и конфликтует с принципом «сайт является источником истины, приложение не хранит профиль».

Для первой версии нового потока:

- вопросы и ответы живут только внутри активной сессии;
- автоматическое запоминание между сессиями отключается;
- неизвестные и чувствительные вопросы по-прежнему требуют пользователя;
- отдельную opt-in функцию «Запоминать мои ответы» можно проектировать позднее, но она не входит в MVP.

Нельзя молча оставить постоянный `ProfileMemory` под другим названием.

## 13. Миграция без большого взрыва

### Этап 1. Новая схема и extractors

- Ввести `SiteResumeSnapshot` и views без удаления старых таблиц.
- Добавить capability и adapter-specific fixtures.
- Реализовать preview/import по feature flag.
- Сравнить новый снимок с текущим импортом на контролируемых резюме.

### Этап 2. Session-scoped candidate context

- Добавить временное хранилище снимков.
- Перевести search planner, evaluator и writer на новый context.
- Добавить локальную подстановку подписи/контактов.
- Перевести восстановление и application answers.
- Новые сессии больше не зависят от `selected_for_matching`.

### Этап 3. Новый UI

- Заменить ProfilePage на импорт резюме внутри создания сессии.
- Удалить файловую загрузку и редакторы.
- Добавить site-specific инструкции и preview.
- Сделать ошибки ссылки понятными и восстановимыми.

### Этап 4. Удаление legacy

- Убрать `/profiles` и resume CRUD после перевода всех потребителей.
- Удалить `backend/services/resume.py`, если он больше не нужен.
- Удалить `CandidateProfile`, `Resume`, `profile_id` и связанные миграции только после анализа внешних ключей.
- Перенести либо удалить `ProfileMemory`, `SessionQuestion` и `ApplicationPlanRecord.candidate_profile_id`.
- Удалить устаревшие frontend types, queries и тесты.
- Очистить legacy-файлы только в явной, безопасной миграции; пользовательские данные нельзя рекурсивно удалять широким filesystem-командованием.

### Этап 5. Включение по умолчанию

- Прогнать миграцию на копии существующей БД и на пустой БД.
- Проверить восстановление незавершённых legacy-сессий либо явно заблокировать несовместимое продолжение понятным сообщением.
- Обновить README и удалить feature flag после периода совместимости.

## 14. Тестовая матрица

### Общие unit-тесты

- выбор adapter capability по `adapter_id`;
- валидация HTTPS, host, port, credentials и path;
- защита от похожих доменов и опасных редиректов;
- раздельные professional/private views;
- отсутствие PII в evaluator и search planner payloads;
- placeholders и локальная подстановка контактов;
- `present/hidden/unsupported/parse_error`;
- стабильный `content_hash`;
- идемпотентное создание и удаление snapshot;
- отсутствие raw URL в логах/events/API responses;
- prompt injection внутри `about`, опыта и дополнительных секций.

### HH.ru fixtures

- полное публичное резюме;
- режим «только по прямой ссылке» без авторизации;
- редирект `hh.ru` → региональный `*.hh.ru`;
- анонимное резюме;
- скрытые контакты;
- несколько мест работы и раскрываемый текст;
- уровни навыков;
- удалённое/недоступное резюме;
- изменившаяся DOM-структура, приводящая к `parse_error`, а не тихой потере полей.

### HireHi fixtures

- полное публичное резюме;
- RU и EN версии;
- проекты, награды, курсы и portfolio;
- отсутствие контактов;
- PDF/ATS ссылки, при этом extractor выбирает HTML;
- снятое с публикации резюме;
- несколько резюме в профиле.

### Zarplata.ru fixtures

Формируются после отдельного UI-аудита и должны включать полный, частичный, анонимный/закрытый и недоступный варианты, если сайт их поддерживает.

### E2E

- пользователь вставляет ссылку, видит preview и запускает сессию;
- поиск и оценка получают professional view;
- письмо получает professional context и локально собранную подпись;
- отклик использует контакты без отправки их evaluator-у;
- падение после импорта восстанавливает ту же версию снимка;
- изменение резюме на сайте не меняет активную сессию;
- завершение формирует результат и удаляет временные данные;
- неправильный сайт/домен не открывается;
- legacy-сессия либо продолжает работать, либо получает заранее определённое сообщение о несовместимости.

## 15. Критерии готовности

Изменение готово, когда:

- HH.ru, HireHi и Zarplata.ru имеют независимые resume extractors;
- новый сайт можно добавить без изменений в resume import service и intelligence-слои;
- пользователь больше не создаёт профиль или резюме внутри приложения;
- file upload и хранение исходных файлов удалены;
- сессия запускается по проверенному site resume snapshot;
- extractor сохраняет site-specific данные без raw HTML;
- модель поиска и оценки не получает прямые персональные данные;
- итоговое письмо корректно содержит выбранные ФИО/контакты через локальную сборку;
- приложение не выводит и не логирует полную публичную ссылку;
- snapshot переживает сбой активной сессии, но удаляется после финализации;
- неизвестный пол не выводится из имени;
- prompt injection из резюме не меняет инструкции модели или браузера;
- README описывает новый пользовательский путь и правила хранения;
- проходят команды из `AGENTS.md`:
  - backend tests и Ruff;
  - frontend tests, typecheck, lint и build;
  - E2E;
  - миграция с пустой БД.

## 16. Не входит в первую реализацию

- редактирование резюме на внешнем сайте из приложения;
- автоматическое объединение резюме разных сайтов;
- автоматическое создание публичной ссылки;
- обход настроек видимости;
- использование скрытых API сайтов;
- OCR изображений резюме внешней моделью;
- постоянный пользовательский профиль под новым названием;
- межсессионное хранение вопросов и ответов без явного opt-in;
- синхронизация резюме посреди уже запущенной сессии.

## 17. Открытые технические решения

Новый чат может принять обоснованное решение в рамках требований:

1. Отдельная таблица snapshot или зашифрованная session recovery entity.
2. Точная реализация безопасного allowlist региональных HH-поддоменов.
3. Формат одноразового preview token.
4. Набор полей, критичных для запуска, и полей, которые можно оставить `hidden/unsupported`.
5. Нужен ли короткий grace period перед удалением terminal snapshot.
6. Способ совместимости с активными legacy-сессиями.
7. Порядок удаления старых profile-related таблиц и foreign keys.

Эти решения не должны менять главные продуктовые требования: site-specific extraction, отсутствие постоянного внутреннего профиля, session-scoped snapshot и минимизация данных для модели.

## 18. Связанный документ
