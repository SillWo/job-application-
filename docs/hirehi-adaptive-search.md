# Адаптивный поиск вакансий HireHi

Статус: проектная спецификация, а не описание полностью реализованного поведения.
Дата фиксации контекста: 12 сентября 2026 года.
Область: поиск и отбор вакансий HireHi для отчёта; автоматическая отправка откликов в эту спецификацию не входит.

## 1. Зачем нужен этот документ

Документ сохраняет контекст обсуждения и целевой алгоритм, чтобы работу можно было продолжить в другом чате без повторного исследования HireHi и повторного согласования метрик.

Главная цель — находить больше релевантных вакансий раньше, не ограничиваясь одной широкой категорией и последовательным просмотром всей её выдачи. Алгоритм должен учиться внутри сессии: перспективные поисковые источники получают больше бюджета, слабые временно охлаждаются, а небольшая доля бюджета остаётся на разведку новых направлений.

Ключевая пользовательская метрика:

```text
R / N
```

где `R` — число релевантных вакансий, а `N` — число уникальных вакансий, полностью проанализированных системой.

## 2. Контекст и исходное состояние

### 2.1. Возможности HireHi, которые надо использовать

На момент исследования интерфейс HireHi предоставлял:

- широкие категории (`менеджмент`, `разработка`, `аналитика` и другие);
- более узкие специализации/подкатегории, например product-management-направления;
- строку поиска по компании, должности и навыкам;
- поисковый синтаксис с обязательными и исключаемыми навыками: `+навык` и `-навык`;
- перечисление альтернатив через запятую как логическое OR;
- фильтры грейда, формата работы, географии, языка, зарплаты и маршрута отклика (`прямой контакт` или HireHi);
- персональные рекомендации вроде Match Me для доступных пользователю тарифов;
- ссылки на похожие вакансии со страницы подходящей вакансии.

Это наблюдаемое поведение внешнего сайта, а не стабильный API-контракт. Перед реализацией каждый элемент нужно повторно подтвердить на актуальном интерфейсе и покрыть mock/E2E-тестом. Работа выполняется только через разрешённую браузерную навигацию и `allowed_domains`; скрытые API HireHi не используются.

### 2.2. Текущее поведение проекта

Существующий `HireHiAdapter`:

- выбирает одну широкую категорию;
- применяет грубый набор грейдов, полученный из стажа;
- при необходимости переключает тип маршрута отклика;
- последовательно обходит страницы одной выдачи;
- запоминает уже найденные ID и восстанавливает позицию после сбоя.

В текущем потоке не используются как единый портфель источников узкие подкатегории, составные поисковые запросы, метаданные карточек, похожие вакансии и статистика качества каждого источника. Поэтому обход хорошо покрывает выбранную выдачу, но расходует много анализа на заведомо слабые сегменты.

### 2.3. Исторические ориентиры

Это не строгий benchmark: выборки получены в разных сессиях и могли отличаться критериями, состоянием выдачи и моделью оценки.

| Сессия/срез | R | N | R/N |
|---|---:|---:|---:|
| Сессия 32, вся выборка | 119 | 420 | 28,3% |
| Сессия 46, вся выборка | 52 | 132 | 39,4% |
| Сессия 46, вакансии с product-названиями | 43 | 75 | 57,3% |
| Сессия 46, вакансии с project-названиями | 8 | 51 | 15,7% |
| Сессия 32, вакансии с product-названиями | 68 | 206 | 33,0% |
| Сессия 32, вакансии с project-названиями | 50 | 207 | 24,2% |

Срез показывает полезный сигнал: разные кластеры поисковой выдачи имеют заметно разную плотность релевантных вакансий. Нельзя навсегда исключать `project` только по этим данным, но разумно динамически перераспределять бюджет в пользу источников, которые дают больше `R` на единицу анализа.

## 3. Термины и единица учёта

- `D` (`discovered`) — число уникальных вакансий, обнаруженных по карточке или ссылке после точной дедупликации, но ещё не обязательно полностью открытых и оценённых.
- `N` (`analyzed`) — число уникальных вакансий, для которых извлечена полная страница и получено конечное решение оценки.
- `R` (`relevant`) — число вакансий из `N` с конечным решением `relevant/apply` по текущим критериям пользователя.
- `R/N` — точность отбора среди полностью проанализированных вакансий.
- `N/D` — покрытие полного анализа; помогает не улучшить `R/N` искусственно за счёт чрезмерного предварительного отсева.
- `source` — воспроизводимый способ получить выдачу: подкатегория, поисковый запрос с фильтрами, рекомендации или похожие вакансии.
- `criteria_hash` — отпечаток нормализованных резюме, предпочтений и порогов оценки. Статистику разных критериев нельзя смешивать напрямую.

Исторические отчёты могли использовать `N` в более широком смысле «найдено и проанализировано», когда почти каждая найденная карточка открывалась. В новой телеметрии `D` и `N` следует хранить раздельно.

Одна вакансия увеличивает `N` и `R` не более одного раза за сессию, независимо от числа источников, в которых она встретилась.

## 4. Поисковый профиль

Перед открытием выдачи система строит структурированный `SearchProfile` из всех выбранных резюме и явных предпочтений пользователя. Текст вакансий не может изменять этот профиль: он считается недоверенными данными.

Минимальные поля профиля:

```yaml
target_roles:          # точные целевые роли
adjacent_roles:        # допустимые соседние роли
excluded_roles:        # явно нежелательные роли
required_skills:
preferred_skills:
excluded_skills:
grades:
locations:
remote_policy:
languages:
salary_floor:
application_types:
hard_constraints:
soft_preferences:
```

Модель может предложить профиль, но результат обязан пройти Pydantic JSON Schema, нормализацию и детерминированные ограничения. Явно заданные пользователем условия имеют приоритет над выводом из резюме.

## 5. Формирование портфеля источников

Вместо одной категории планировщик создаёт 8–12 достаточно разных источников. Одновременно активны не более 12, чтобы статистика не распылялась.

Рекомендуемые семейства источников:

1. Точная подкатегория целевой роли.
2. Поиск по точному названию роли и его безопасным синонимам.
3. Запросы по сочетанию роли и обязательных навыков.
4. Узкие skill-first запросы для вакансий с нестандартным названием.
5. Допустимые соседние роли.
6. Широкая категория как источник покрытия и контрольная группа.
7. Персональные рекомендации, если они доступны текущему пользователю.
8. Похожие вакансии, обнаруженные на страницах уже релевантных вакансий.

Примеры-кандидаты для product-профиля (точный синтаксис надо подтвердить в актуальном UI):

```text
product manager, product owner
product manager +B2B +SaaS
product owner +аналитика -gambling
growth product, product growth +эксперименты
```

Источники должны различаться не только строкой, но и ожидаемой ролью в портфеле. Почти одинаковые запросы объединяются до запуска. У каждого источника хранятся:

```text
source_id, family, query/filter spec, cluster,
raw_discovered, unique_discovered, analyzed, relevant,
duplicates, failures, elapsed_seconds,
cursor/page, exhausted, cooldown_until, last_used_at
```

## 6. Двухступенчатый отбор

### 6.1. Быстрый этап по карточке

До дорогого открытия страницы карточка получает детерминированные признаки и дешёвый предварительный балл:

- совпадение роли и допустимых синонимов;
- обязательные/исключённые слова;
- компания, грейд, локация, формат, язык и зарплата, если они видны;
- уже просмотренный ID или канонический URL;
- известный нежелательный кластер.

Жёсткий фильтр применяется только к однозначным нарушениям явных требований. Неизвестное значение не считается отрицательным. Всё остальное ранжируется и поступает на полный анализ в порядке приоритета.

Чтобы измерять ошибки предварительного фильтра, случайные 10% отброшенных карточек проходят полный анализ как audit sample. Они учитываются отдельно и позволяют оценивать false-negative rate.

### 6.2. Полный анализ

Для выбранной вакансии адаптер извлекает нормализованный `JobPosting`, после чего общий evaluator принимает решение по неизменным критериям пользователя. Только конечное решение увеличивает `N`; релевантное решение одновременно увеличивает `R`.

Причина нерелевантности должна быть структурированной, например:

```text
wrong_role | wrong_grade | hard_skill_missing | excluded_domain |
location | work_format | language | salary | insufficient_evidence | other
```

Эта причина используется для объяснения, аудита и генерации следующих источников. Она не должна автоматически превращать случайную фразу из вакансии в новое пользовательское правило.

## 7. Адаптивный планировщик

### 7.1. Калибровка

В начале сессии каждый стартовый источник получает небольшой одинаковый бюджет — по умолчанию до 10 уникальных полных анализов. Если источник закончился раньше, это фиксируется как нормальное исчерпание, а не ошибка.

После калибровки статистика источника `s` задаёт апостериорное распределение его вероятности релевантности:

```text
theta_s ~ Beta(R_s + 1, N_s - R_s + 1)
```

Нулевая история поэтому не означает нулевое качество, а источники с малой выборкой сохраняют шанс на дополнительную проверку.

### 7.2. Выбор следующего источника

В 80% раундов используется exploitation: Thompson Sampling выбирает источник с наибольшим скорректированным результатом. В 20% — exploration: выбирается новый, малоизученный или недавно изменившийся источник.

Для активного источника:

```text
sample_s = sample(Beta(R_s + 1, N_s - R_s + 1))
score_s  = sample_s * novelty_s * availability_s / (1 + lambda * cost_s)
```

где:

- `novelty_s` — сглаженная доля новых уникальных вакансий среди найденных;
- `availability_s` — оценка того, что в источнике остались результаты;
- `cost_s` — нормализованное относительно медианы время полного анализа одной вакансии;
- `lambda` — настраиваемый вес стоимости.

Первый релевантный результат засчитывается источнику первого обнаружения. Остальные источники, где встретился тот же ID, получают запись overlap, но не дополнительный `R` или `N`. В отчёте сохраняются все источники происхождения, чтобы позднее проверить альтернативные схемы attribution.

### 7.3. Размеры порций

Значения по умолчанию, которые должны стать конфигурацией, а не магическими числами:

- калибровка: до 10 анализов на стартовый источник;
- обычный раунд: 8 анализов;
- уверенный exploitation: до 15 анализов;
- exploration: 5 анализов.

После каждой порции обновляются `R`, `N`, новизна, стоимость и состояние курсора. Состояние сохраняется до следующей значимой навигации.

### 7.4. Охлаждение и реактивация

Источник можно отправить в cooldown, если:

- накоплено не менее 25 полных оценок;
- верхняя граница доверительного интервала качества ниже текущей рабочей цели или источник существенно хуже портфеля;
- низкий результат не объясняется временной ошибкой, малым покрытием или чрезмерным предварительным фильтром.

Cooldown — не вечный ban. Источник возвращается после нескольких раундов, появления новых результатов, изменения критериев или исчерпания более сильных источников. Широкий контрольный источник всегда периодически получает небольшой бюджет.

## 8. Расширение поиска по обратной связи

После каждых примерно 50 полных оценок либо при падении новизны планировщик может предложить новый ограниченный набор источников. Входные данные:

- исходный `SearchProfile`;
- агрегированные причины отказов;
- безопасно очищенные примеры релевантных вакансий;
- уже использованные запросы и их статистика.

Полезные сигналы:

- несколько релевантных вакансий используют один и тот же вариант названия роли;
- релевантные вакансии стабильно приходят из конкретной подкатегории;
- обязательный навык часто встречается в нестандартно названных ролях;
- похожие вакансии дают высокий `R/N` и достаточную новизну.

Новый источник проходит валидацию, дедупликацию с портфелем и получает только exploration-бюджет. Модель не управляет браузером и не создаёт произвольные URL.

## 9. Дедупликация

Дедупликация выполняется в два слоя:

1. Точная: внешний ID и нормализованный канонический URL. Такая вакансия открывается и оценивается один раз.
2. Семантическая: одинаковая компания, близкое название, совпадающая локация и почти идентичное описание.

Семантический слой не должен склеивать просто похожие вакансии одной компании. Уверенный near-duplicate может повторно использовать извлечённый текст/оценку, но исходные ссылки и все появления сохраняются. Неуверенные пары остаются разными вакансиями.

## 10. Остановка

Сессия завершается при первом применимом условии:

- достигнут пользовательский лимит релевантных вакансий для отчёта;
- все активные источники исчерпаны, а расширение не добавило новых;
- достигнут лимит времени, полного анализа или стоимости;
- пользователь остановил сессию;
- возник блокер, требующий человека.

«Источник исчерпан» означает только окончание наблюдаемой выдачи этого источника в текущей эпохе. Это не утверждение, что просмотрен весь HireHi. Рекомендации и динамические выдачи могут обновляться, поэтому для них используется контролируемый refresh с backoff.

## 11. Состояние и восстановление

Checkpoint должен включать:

```yaml
algorithm_version: hirehi_adaptive_v1
criteria_hash:
profile_snapshot:
portfolio:
source_stats:
source_cursors:
pending_refs:
seen_exact_ids:
semantic_clusters:
origin_map:
analyzed_ids:
relevant_ids:
audit_sample_state:
exploration_rng_state:
next_expansion_at:
budgets:
```

Checkpoint сохраняется после добавления источника, обнаружения порции, полного решения, изменения cooldown и расширения портфеля. Восстановление обязано быть идемпотентным: повтор после сбоя не создаёт второй `N`, второй `R` или дубликат строки отчёта.

Статистику между сессиями можно переносить только при совместимом `criteria_hash` и версии алгоритма. Без достаточного совпадения она используется как слабый prior либо не используется вовсе.

## 12. Метрики и проверка результата

Обязательные метрики сессии:

- `D`, `N`, `R`, `R/N`, `N/D`;
- `R@50`, `R@100`, `R@200` — сколько релевантных найдено среди первых `k` полных анализов;
- `R/N@50`, `R/N@100`, `R/N@200`;
- время до `R=1/20/50/100`;
- число сырых находок, точных дублей и semantic near-duplicates;
- качество, новизна, стоимость и ошибки по каждому источнику;
- доля exploration и exploitation;
- доля и false-negative rate audit sample;
- покрытие причин отказа;
- версия кода, модели, критериев и поискового алгоритма.

### Сравнение с baseline

Сначала алгоритм запускается в shadow/benchmark-режиме без изменения пользовательских действий. Для baseline и adaptive нужны одинаковые:

- резюме и предпочтения;
- пороги evaluator;
- лимит `N` или времени;
- версия модели;
- временное окно, насколько это практически возможно.

Сравниваются прежде всего кривые `R@N`, а не только финальный `R/N`: адаптивный вариант должен находить релевантные вакансии раньше и не терять заметную долю общего `R`. Решение о включении нельзя принимать по одной сессии; нужны повторные парные прогоны и интервалы неопределённости.

## 13. Размещение по архитектурным слоям

Разделение ответственности проекта сохраняется:

- `backend/adapters/hirehi` — только безопасная навигация HireHi, локаторы, извлечение карточек/вакансий/видимых источников и пагинация;
- `backend/intelligence` — построение `SearchProfile`, предложение ограниченного портфеля и структурированные схемы через `ModelGateway`;
- `backend/orchestrator` — state machine, adaptive scheduler, бюджеты, cooldown, очереди и checkpoint;
- `backend/services` — расчёт метрик, сравнение baseline и adaptive, подготовка отчёта;
- `backend/persistence` — долговечные source stats, события и версия алгоритма без cookies, паролей и browser storage;
- API/frontend — только настройка бюджета, показ прогресса и объяснимых метрик, если это потребуется продукту.

Адаптер не оценивает релевантность, не пишет резюме/письма, не принимает решения о бюджете и не хранит статистическую модель.

## 14. Поэтапная реализация

### V1 — детерминированный портфель

- Зафиксировать схемы `SearchProfile`, `SearchSource`, `SourceStats` и checkpoint.
- Научить адаптер читать узкие категории, строку поиска, фильтры и похожие вакансии через UI.
- Добавить 8–12 источников, round-robin с фиксированными порциями, точную дедупликацию и раздельные `D/N/R`.
- Добавить карточный pre-rank, 10% audit sample и полный отчёт метрик.
- Провести shadow-сравнение с текущим `hirehi_v1`.

### V2 — адаптивное распределение

- Включить Thompson Sampling, 80/20 exploration, новизну, стоимость и availability.
- Добавить cooldown/reactivation и ограничение активного портфеля.
- Проверить устойчивость к малым выборкам, пустым выдачам, повторным страницам и сбоям восстановления.

### V3 — обучение между сессиями

- Добавить weak priors по совместимому `criteria_hash`.

## 15. Критерии готовности

Изменение считается готовым, когда:

- новый поток можно включать флагом версии и безопасно откатить на `hirehi_v1`;
- после падения процесс продолжает тот же источник и не удваивает `D`, `N`, `R` или отчёт;
- неизвестные данные карточки не превращаются в жёсткий отказ;
- audit sample измеряет потери предварительного фильтра;
- неизвестный или сгенерированный URL не проходит allowlist-валидацию;
- текст вакансии не может изменить профиль, запросы или браузерные команды;
- есть unit-тесты планировщика и checkpoint, mock-страницы адаптера и E2E-сценарий восстановления;
- проходят backend tests/Ruff, frontend tests/typecheck/lint/build, E2E и миграция с пустой БД;
- README описывает новую версию поиска и интерпретацию `D`, `N`, `R`;
- на серии сопоставимых прогонов adaptive улучшает раннюю кривую `R@N`, а падение итогового количества релевантных вакансий остаётся в заранее согласованном допуске.

## 16. Открытые решения перед кодом

Перед реализацией нужно повторно проверить и явно зафиксировать:

1. Актуальные URL/локаторы узких подкатегорий и способ кодирования поисковой строки и фильтров.
2. Доступность рекомендаций Match Me без PRO и допустимость их использования в конкретной сессии.
3. Точный критерий semantic near-duplicate и допустимо ли переиспользовать оценку без второго открытия.
4. Целевой лимит: по `R`, `N`, времени или их комбинации.
5. Порог false-negative rate для карточного фильтра.
6. Правило cooldown: доверительный уровень, рабочая цель качества и длина паузы.
7. Допустимое снижение полного `R` ради ускорения раннего поиска.

До ответа на эти вопросы безопасный стартовый вариант — V1 с точной дедупликацией, фиксированным бюджетом, без межсессионного обучения и без автоматического semantic skip.
