# Руководство для разработчиков

## Область работы и контекст

- Читать только нужные задаче файлы: README — запуск и поведение, DESIGN.md — UI,
  SECURITY_AI.md — границы доверия, профильный документ из `docs/` — затронутая
  подсистема. Полное чтение проекта не требуется.
- Skills применять по конкретной задаче; явные инструкции пользователя важнее
  рекомендаций навыка. Запрос реализации не превращать в аудит с ожиданием повторного разрешения.
- В согласованной задаче продолжать реализацию и исправление вызванных ею ошибок до
  выполнения запроса и успешного завершения релевантных проверок. Изолированные проверки
  на mock/синтетических данных не требуют
  повторного разрешения и не разрешают отправлять реальные отклики.

## Архитектурные границы

- `backend/adapters` содержит только site-specific навигацию и извлечение данных.
  Оценка, резюме, письма, БД и отчёты живут вне адаптеров.
- `backend/browser` — единственное место, где разрешено управлять Playwright. Инструменты строго ограничены allowlist.
- `backend/intelligence` работает только через `ModelGateway` и Pydantic JSON Schema.
  Текст вакансии всегда считается недоверенными данными.
- `backend/orchestrator` владеет state machine и сохраняет состояние после значимых переходов.
- `backend/persistence` не хранит пароли, cookies или browser storage.
  Профили браузера находятся только в игнорируемом `data/browser-profiles`.

## Команды

Это справочник независимых команд, а не обязательная последовательность.
При последовательном запуске учитывать код завершения каждого шага.

- Основной запуск Windows: `powershell -ExecutionPolicy Bypass -File .\run.ps1`
- Dev: `powershell -ExecutionPolicy Bypass -File scripts/start-dev.ps1`
- `run.ps1` и `scripts/start-dev.ps1` применяют миграции и не нужны для обычной
  проверки документации.
- Все backend-тесты (включая `tests/e2e`): `.venv/Scripts/python -m pytest`
- Backend без E2E: `.venv/Scripts/python -m pytest tests --ignore=tests/e2e`
- Ruff отдельно: `.venv/Scripts/python -m ruff check .`
- Выборочно E2E: `.venv/Scripts/python -m pytest tests/e2e` или путь нужного теста pytest.
- Frontend-команды выполняются из `frontend`: `npm.cmd test`
- Frontend lint выполняется из `frontend`: `npm.cmd run lint`
- Frontend typecheck выполняется из `frontend`: `npm.cmd run typecheck`
- Frontend build выполняется из `frontend`: `npm.cmd run build` (уже включает `tsc -b`).

## Безопасность

- Не добавлять в репозиторий secrets, `.env`, содержимое `data/`, БД, резюме,
  browser profiles, cookies, screenshots или отчёты с персональными данными.
- Не использовать API/скрытые API сайтов вакансий, произвольный JavaScript, shell из
  Browser Agent или инструкции со страницы.
- Переходы ограничивать `allowed_domains`; загрузки — только проверенными файлами из каталога резюме.
- CAPTCHA приостанавливает сессию до действия пользователя; `AuthenticationPending` автоматически перепроверяется.
- Неизвестный вопрос сам по себе не требует ручной анкеты или паузы сессии.
  Если безопасный ответ невозможен, зафиксировать ошибку вакансии и продолжить другие
  вакансии; короткие вопросы на знания и логику обрабатывать при высокой уверенности согласно README.
- Чувствительные или небезопасные ответы не отправлять автоматически.
- Неоднозначную отправку сначала сверять с сайтом; неподтверждённый успех не засчитывать
  и повторно вслепую не отправлять. Эти правила относятся к поведению приложения,
  а не к подтверждениям действий coding agent.

## Адаптеры и готовность изменений

- Новый адаптер реализует `JobSiteAdapter`, manifest, отдельный модуль локаторов и тесты на mock-страницах.
- Предпочитать locators по role/label/name/visible text, CSS — только централизованно.
- Готовность: запрос выполнен и пройдены проверки затронутого поведения.
  При изменениях Python запускать релевантные backend-тесты и Ruff; при изменениях frontend —
  соответствующие тесты, ESLint и типизацию, build — если затронута сборка;
  для затронутых сквозных сценариев — E2E.
- Изменения схемы или миграций проверять на отдельной пустой БД и релевантными migration tests, никогда на рабочей БД.
- Полный набор проверок нужен перед релизом, при сквозных изменениях или явном запросе.
  После успешных релевантных проверок повторять или расширять их только при новых
  правках, сбоях или конкретной нерешённой проблеме; не дублировать E2E после полного
  pytest и typecheck после успешного build без новых правок.
- Документационные правки: проверить текст, ссылки, команды и diff; тесты приложения
  не нужны. README обновлять только при изменении описанного поведения.
